Glosario Arquitectónico y Conceptos Esenciales

Domina la distinción rigurosa de cada componente en la nube. Cada término incluye su definición formal, una analogía práctica para interiorizar el concepto y la evidencia exacta de cómo se aplicó en los laboratorios.

S05 Red vs Autorización

Reachability (Alcance de Red)

Capacidad de un paquete IP para viajar desde una interfaz de red (ENI en EC2) hasta el endpoint del servicio AWS a través de la infraestructura de enrutamiento (IGW, tablas de ruta y Security Groups).

💡 Concepto Intuitivo / Analogía Práctica: Tener una carretera pavimentada y el portón abierto para llegar hasta la puerta del banco. Que puedas pararte en la puerta no significa que el vigilante te deje abrir la caja fuerte.
🛠️ Aplicación Exacta en el Laboratorio: En el Lab 05 configuramos Internet Gateway y ruta 0.0.0.0/0 en Subnet A para que la EC2 alcance el endpoint público de S3. Si la red falla, la respuesta es 'Could not connect / Timeout', jamás 'AccessDenied'.
S05 Control de Acceso

Authorization (Autorización IAM)

Evaluación formal donde el motor de políticas de AWS determina si la identidad autenticada tiene permiso para ejecutar una acción específica (Action) sobre un recurso determinado (Resource).

💡 Concepto Intuitivo / Analogía Práctica: El oficial de seguridad revisando tu identificación contra el libro de registros para decidir si puedes acceder a la bóveda A o a la bóveda B.
🛠️ Aplicación Exacta en el Laboratorio: La misma instancia EC2 con el mismo IAM Role leyó con éxito 'allowed/context.txt' (PASS) pero recibió 'AccessDenied' al solicitar 'restricted/secret.txt'.
S05 Gestión de Identidades

IAM Role & Credenciales Temporales

Identidad de IAM sin credenciales estáticas permanentes, asumida por servicios como EC2 o Lambda mediante AWS Security Token Service (STS) que entrega llaves temporales autogestionadas.

💡 Concepto Intuitivo / Analogía Práctica: Un carnet digital con chip de radiofrecuencia que se renueva y expira automáticamente cada pocas horas, eliminando el riesgo de extraviar llaves maestras físicas.
🛠️ Aplicación Exacta en el Laboratorio: Eliminó la necesidad de ejecutar 'aws configure' o almacenar credenciales fijas (Access Key / Secret Key) dentro de la EC2 o en el código de Lambda.
S05 EC2 + IAM

Instance Profile (Perfil de Instancia)

Contenedor que permite asociar un rol de IAM a una instancia EC2 en tiempo de inicialización o en caliente.

💡 Concepto Intuitivo / Analogía Práctica: El porta-carnet físico con cordón donde insertas el chip de permisos para que el servidor lo porte consigo.
🛠️ Aplicación Exacta en el Laboratorio: Al crear el rol 'dcl-dev-role-s05' en la consola para el servicio EC2, AWS generó automáticamente un Instance Profile homónimo para asociarlo a la instancia virtual.
S05 Estructura JSON

IAM Policy: Action vs Resource

'Action' especifica la operación o verbo API permitido o denegado (ej. s3:GetObject). 'Resource' restringe el objeto o ARN específico sobre el cual recae dicha operación.

💡 Concepto Intuitivo / Analogía Práctica: 'Action' es el verbo 'Leer', mientras que 'Resource' es el estante número 1. Si intentas 'Escribir' o 'Leer el estante 2', la petición es rechazada.
🛠️ Aplicación Exacta en el Laboratorio: Con Action: 's3:GetObject' y Resource: 'arn:aws:s3:::bucket/allowed/*', leer en restricted/ falló por Resource y escribir en allowed/ falló por Action.
S05 Permisos S3

s3:GetObject vs s3:PutObject

's3:GetObject' concede permiso de lectura y descarga de bytes de un objeto existente. 's3:PutObject' autoriza la carga, creación o sobrescritura de objetos.

💡 Concepto Intuitivo / Analogía Práctica: GetObject es consultar un expediente existente; PutObject es archivar un documento nuevo en el archivador.
🛠️ Aplicación Exacta en el Laboratorio: Se validó que el rol tuviera únicamente s3:GetObject, verificando que los intentos de s3:PutObject fueran rechazados con AccessDenied de manera sistemática.
S05 Cifrado en Reposo

SSE-S3 (Server-Side Encryption)

Cifrado del lado del servidor gestionado por Amazon S3 (AES-256). Protege los bloques físicos de datos almacenados en los discos del centro de datos.

💡 Concepto Intuitivo / Analogía Práctica: Cerrar los archivadores con llave en la bodega del banco. Protege ante el robo del mueble físico, pero no decide si un empleado tiene autorización para consultar los expedientes.
🛠️ Aplicación Exacta en el Laboratorio: Cifrar el bucket con SSE-S3 demostró que el cifrado en reposo no influye en las decisiones de autorización ni produce errores de AccessDenied para usuarios autorizados.
S05 Auditoría & Trazabilidad

CloudTrail: Management vs Data Events

Management Events registran operaciones de plano de control (crear roles, asociar políticas). Data Events registran operaciones de plano de datos (leer/escribir objetos S3, invocar Lambdas).

💡 Concepto Intuitivo / Analogía Práctica: Management Events es el libro de actas notarial de contratación del personal. Data Events es la cámara que graba cada vez que alguien saca una hoja del cajón.
🛠️ Aplicación Exacta en el Laboratorio: En el Event History de CloudTrail se auditó 'AttachRolePolicy' (Management Event). No se visualizan 'GetObject' ni 'PutObject' porque corresponden a Data Events que requieren trails dedicados.
S06 Infraestructura como Código (IaC)

CloudFormation: Template vs Stack

El Template es la declaración declarativa en YAML/JSON del estado deseado. El Stack es la colección unificada de recursos aprovisionados y gestionados colectivamente.

💡 Concepto Intuitivo / Analogía Práctica: El Template es el plano arquitectónico en papel; el Stack es la edificación real construida y lista para operar.
🛠️ Aplicación Exacta en el Laboratorio: El archivo fuente fue 's06-ops-cloudformation.yaml' y la unidad aprovisionada en la cuenta fue el stack 'dcl-dev-stack-ops-s06'.
S06 CloudFormation

Logical ID vs Physical ID

El Logical ID es el identificador simbólico dentro de la plantilla. El Physical ID es el identificador único e inmutable asignado por AWS al crear el recurso en el entorno.

💡 Concepto Intuitivo / Analogía Práctica: Logical ID es la etiqueta 'VehículoDeCarga' en el contrato; Physical ID es la placa de matrícula 'i-09f42b...' asignada por el registro vehicular.
🛠️ Aplicación Exacta en el Laboratorio: El recurso lógico 'OpsInstance' del YAML se materializó en AWS con el Physical ID 'i-0123456789abcdef0'.
S06 Ciclo de Vida IaC

Update sin Reemplazo (In-Place)

Actualización de un stack donde los cambios se aplican a propiedades no críticas (como Tags o descripciones) sin requerir la destrucción y recreación del recurso.

💡 Concepto Intuitivo / Analogía Práctica: Cambiar la etiqueta identificadora en una máquina industrial sin necesidad de desarmarla ni detener la fábrica.
🛠️ Aplicación Exacta en el Laboratorio: Se actualizó el parámetro 'LabRevision' de v1 a v2, validando que el InstanceId de la instancia EC2 se mantuvo idéntico antes y después de la operación.
S06 Métricas CloudWatch

Basic Monitoring en Amazon EC2

Monitoreo estándar sin costo adicional provisto por el hipervisor de AWS, con granularidad de métricas cada 5 minutos (300 segundos).

💡 Concepto Intuitivo / Analogía Práctica: Un supervisor que realiza un control de temperatura cada 5 minutos exactos en lugar de monitorear segundo a segundo.
🛠️ Aplicación Exacta en el Laboratorio: Dado que cada datapoint toma 5 minutos y la alarma requiere 2 períodos consecutivos, la carga de UserData debió sostenerse durante 15 minutos (900 s).
S06 Alarmas CloudWatch

Period, EvaluationPeriods y DatapointsToAlarm

Period: tamaño de la ventana de agregación (300 s). EvaluationPeriods: cantidad de ventanas recientes analizadas (2). DatapointsToAlarm: cantidad de períodos anómalos requeridos para cambiar a estado ALARM (2).

💡 Concepto Intuitivo / Analogía Práctica: Para emitir una alerta, el sistema exige comprobar que en 2 mediciones consecutivas de 5 minutos el promedio superó el 70%.
🛠️ Aplicación Exacta en el Laboratorio: La alarma inició en estado 'INSUFFICIENT_DATA' hasta completar la recolección de los dos períodos de métricas requeridos.
S06 Automatización de Arranque

UserData en Amazon EC2

Script de shell ejecutado con privilegios de root una única vez durante el primer inicio de la instancia para configuración y arranque autónomo.

💡 Concepto Intuitivo / Analogía Práctica: La lista de instrucciones preprogramadas que ejecuta un dispositivo al encenderse por primera vez de fábrica.
🛠️ Aplicación Exacta en el Laboratorio: Se ejecutaron 2 bucles de saturación de CPU con 'timeout 900 bash -c "while :; do :; done"' sin requerir conexión SSH ni acceso a Internet.
S07 Modernización

Arquitectura Orientada a Eventos (Serverless)

Patrón desacoplado donde los componentes reaccionan a cambios de estado emitidos por un productor (S3) mediante la ejecución efímera de funciones (Lambda).

💡 Concepto Intuitivo / Analogía Práctica: Un timbre que suena solo cuando llega un paquete, en lugar de mantener a una persona esperando 24/7 en la puerta.
🛠️ Aplicación Exacta en el Laboratorio: La subida de 'incoming/order-001.json' generó el evento 'ObjectCreated:Put' que invocó a Lambda durante escasos ~2 milisegundos.
S07 Seguridad en Lambda

Execution Role vs Resource-based Policy

Resource-based Policy: autoriza la invocación entrante (de S3 a Lambda). Execution Role: autoriza las llamadas salientes (de Lambda a CloudWatch Logs).

💡 Concepto Intuitivo / Analogía Práctica: Resource-based policy es la autorización que permite a la oficina postal tocar a tu puerta; Execution Role es tu credencial para redactar reportes en el archivo central.
🛠️ Aplicación Exacta en el Laboratorio: Al configurar el trigger de S3 se generó la Resource-based policy; el Execution Role 'dcl-dev-role-lambda-s07' se configuró exclusivamente con permisos de escritura de logs.
S07 Disparadores de Eventos

Filtros de Notificación S3 (Prefix & Suffix)

Criterios de coincidencia en el productor de eventos que restringen el disparo de notificaciones según el prefijo (carpeta) y sufijo (extensión) del objeto.

💡 Concepto Intuitivo / Analogía Práctica: Filtrar la bandeja de correspondencia para tramitar únicamente cartas que provengan de la carpeta 'incoming/' y terminen en formato '.json'.
🛠️ Aplicación Exacta en el Laboratorio: Se configuró Prefix='incoming/' y Suffix='.json', previniendo activamente bucles infinitos de auto-invocación recursiva.
S07 CloudWatch Logs

Log Group Precreado y Retención

Creación anticipada del contenedor de logs en CloudWatch con política de retención explícita (1 día), acotando los permisos requeridos por el rol de Lambda.

💡 Concepto Intuitivo / Analogía Práctica: Habilitar un cuaderno de registros con vigencia de un día para que el operador solo tenga permiso de escribir, sin facultades para crear cuadernos arbitrarios.
🛠️ Aplicación Exacta en el Laboratorio: Precrear '/aws/lambda/dcl-dev-order-event-s07' permitió retirar 'logs:CreateLogGroup' del rol, dejando únicamente 'CreateLogStream' y 'PutLogEvents'.
S07 Semántica de Eventos

Garantía de Entrega At-Least-Once

Garantía de los sistemas de mensajería distribuida donde AWS asegura que todo evento llegará al menos una vez al consumidor, pudiendo presentar duplicados esporádicos.

💡 Concepto Intuitivo / Analogía Práctica: Un mensajero que ante la duda de si recibiste el mensaje, te entrega una segunda copia de seguridad.
🛠️ Aplicación Exacta en el Laboratorio: La presencia eventual de dos ejecuciones en CloudWatch para un mismo objeto es inherente a la arquitectura distribuida de Amazon S3 y no un error de diseño.

Paso 1

Paso 1 — Crear el Bucket y los Dos Objetos

▼
🛠️ Qué hacemos:
Crear un bucket S3 privado y dos objetos existentes bajo prefijos distintos.
🧠 Por qué:
El objeto restricted debe existir antes del AccessDenied; de lo contrario, un error de nombre o un recurso inexistente podría confundirse con autorización.
📋 Procedimiento Detallado (Pasito a Pasito del Profesor):
  • ▸ 7. En S3, creen dcl-s05-teamXX-<account-id> en us-east-1.
  • ▸ 8. Mantengan Block Public Access habilitado. No creen bucket policy para este lab.
  • ▸ 9. Mantengan Default encryption en SSE-S3. No utilicen una customer managed KMS key.
  • ▸ 10. Suban allowed/context.txt con un texto breve como 'Digital Café Luna — lectura autorizada'.
  • ▸ 11. Suban restricted/secret.txt con un texto breve diferente, por ejemplo 'Digital Café Luna — recurso restringido'.
  • ▸ 12. No habiliten Versioning; S03 ya cubrió ese comportamiento.
Comandos Oficiales AWS CLI 
# 1. Crear bucket S3 privado en us-east-1 con Block Public Access estricto
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
BUCKET="dcl-s05-team01-${ACCOUNT_ID}"
aws s3api create-bucket --bucket "$BUCKET" --region us-east-1

aws s3api put-public-access-block --bucket "$BUCKET" \
  --public-access-block-configuration "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true"

# 2. Subir ambos objetos de texto
echo "Digital Café Luna — lectura autorizada" > context.txt
echo "Digital Café Luna — recurso restringido" > secret.txt
aws s3 cp context.txt "s3://${BUCKET}/allowed/context.txt"
aws s3 cp secret.txt "s3://${BUCKET}/restricted/secret.txt"
✅ Validación Oficial:
Ambos objetos existen en el mismo bucket; el bucket es privado; Default encryption muestra SSE-S3.
📷 Evidencia Exigida para la Entrega:
Registren el nombre del bucket y la vista donde se observan ambos keys. Esta captura apoya la prueba, pero no sustituye la evidencia de autorización efectiva.
🎯 Ojo Técnico / Foco de Examen: SSE-S3 cifra datos at rest. NO tiene relación con quién recibe AccessDenied. Quien bloquea o permite es la política de IAM.
Paso 2

Paso 2 — Crear Policy, Role e Instance Profile

▼
🛠️ Qué hacemos:
Crear una policy mínima y asociarla a un IAM Role para EC2.
🧠 Por qué:
El workload necesita una identidad con permisos precisos. El IAM console crea el instance profile de EC2 con el mismo nombre del role; ese profile es el contenedor que entrega el role a la instancia.
📋 Procedimiento Detallado (Pasito a Pasito del Profesor):
  • ▸ Creen primero la customer managed policy dcl-dev-policy-s3-read-allowed-s05 usando el JSON siguiente. Sustituyan BUCKET_NAME por el nombre real; no agreguen s3:ListBucket, s3:* ni Resource: '*'.
  • ▸ 13. Creen dcl-dev-role-s05 con trusted entity = AWS service y use case = EC2.
  • ▸ 14. Adjunten dcl-dev-policy-s3-read-allowed-s05 al role. Hagan esta asociación explícitamente: generará un management event AttachRolePolicy útil para CloudTrail.
  • ▸ 15. Confirmen que el role no tenga otras policies que otorguen acceso S3 y que el instance profile dcl-dev-role-s05 esté disponible para EC2.

Glosario Técnico de este Laboratorio (S06)

6 Términos Clave
▼

Conceptos arquitectónicos evaluados estrictamente en esta práctica. Consulta su significado formal y aplicación directa.

CloudFormation: Template vs Stack

Definición: El Template es la declaración declarativa en YAML/JSON del estado deseado. El Stack es la colección unificada de recursos aprovisionados y gestionados colectivamente.

💡 Analogía: El Template es el plano arquitectónico en papel; el Stack es la edificación real construida y lista para operar.

🛠️ En este Lab: El archivo fuente fue 's06-ops-cloudformation.yaml' y la unidad aprovisionada en la cuenta fue el stack 'dcl-dev-stack-ops-s06'.

Logical ID vs Physical ID

Definición: El Logical ID es el identificador simbólico dentro de la plantilla. El Physical ID es el identificador único e inmutable asignado por AWS al crear el recurso en el entorno.

💡 Analogía: Logical ID es la etiqueta 'VehículoDeCarga' en el contrato; Physical ID es la placa de matrícula 'i-09f42b...' asignada por el registro vehicular.

🛠️ En este Lab: El recurso lógico 'OpsInstance' del YAML se materializó en AWS con el Physical ID 'i-0123456789abcdef0'.

Update sin Reemplazo (In-Place)

Definición: Actualización de un stack donde los cambios se aplican a propiedades no críticas (como Tags o descripciones) sin requerir la destrucción y recreación del recurso.

💡 Analogía: Cambiar la etiqueta identificadora en una máquina industrial sin necesidad de desarmarla ni detener la fábrica.

🛠️ En este Lab: Se actualizó el parámetro 'LabRevision' de v1 a v2, validando que el InstanceId de la instancia EC2 se mantuvo idéntico antes y después de la operación.

Basic Monitoring en Amazon EC2

Definición: Monitoreo estándar sin costo adicional provisto por el hipervisor de AWS, con granularidad de métricas cada 5 minutos (300 segundos).

💡 Analogía: Un supervisor que realiza un control de temperatura cada 5 minutos exactos en lugar de monitorear segundo a segundo.

🛠️ En este Lab: Dado que cada datapoint toma 5 minutos y la alarma requiere 2 períodos consecutivos, la carga de UserData debió sostenerse durante 15 minutos (900 s).

Period, EvaluationPeriods y DatapointsToAlarm

Definición: Period: tamaño de la ventana de agregación (300 s). EvaluationPeriods: cantidad de ventanas recientes analizadas (2). DatapointsToAlarm: cantidad de períodos anómalos requeridos para cambiar a estado ALARM (2).

💡 Analogía: Para emitir una alerta, el sistema exige comprobar que en 2 mediciones consecutivas de 5 minutos el promedio superó el 70%.

🛠️ En este Lab: La alarma inició en estado 'INSUFFICIENT_DATA' hasta completar la recolección de los dos períodos de métricas requeridos.

UserData en Amazon EC2

Definición: Script de shell ejecutado con privilegios de root una única vez durante el primer inicio de la instancia para configuración y arranque autónomo.

💡 Analogía: La lista de instrucciones preprogramadas que ejecuta un dispositivo al encenderse por primera vez de fábrica.

🛠️ En este Lab: Se ejecutaron 2 bucles de saturación de CPU con 'timeout 900 bash -c "while :; do :; done"' sin requerir conexión SSH ni acceso a Internet.

Glosario Técnico de este Laboratorio (S07)

5 Términos Clave
▼

Conceptos arquitectónicos evaluados estrictamente en esta práctica. Consulta su significado formal y aplicación directa.

Arquitectura Orientada a Eventos (Serverless)

Definición: Patrón desacoplado donde los componentes reaccionan a cambios de estado emitidos por un productor (S3) mediante la ejecución efímera de funciones (Lambda).

💡 Analogía: Un timbre que suena solo cuando llega un paquete, en lugar de mantener a una persona esperando 24/7 en la puerta.

🛠️ En este Lab: La subida de 'incoming/order-001.json' generó el evento 'ObjectCreated:Put' que invocó a Lambda durante escasos ~2 milisegundos.

Execution Role vs Resource-based Policy

Definición: Resource-based Policy: autoriza la invocación entrante (de S3 a Lambda). Execution Role: autoriza las llamadas salientes (de Lambda a CloudWatch Logs).

💡 Analogía: Resource-based policy es la autorización que permite a la oficina postal tocar a tu puerta; Execution Role es tu credencial para redactar reportes en el archivo central.

🛠️ En este Lab: Al configurar el trigger de S3 se generó la Resource-based policy; el Execution Role 'dcl-dev-role-lambda-s07' se configuró exclusivamente con permisos de escritura de logs.

Filtros de Notificación S3 (Prefix & Suffix)

Definición: Criterios de coincidencia en el productor de eventos que restringen el disparo de notificaciones según el prefijo (carpeta) y sufijo (extensión) del objeto.

💡 Analogía: Filtrar la bandeja de correspondencia para tramitar únicamente cartas que provengan de la carpeta 'incoming/' y terminen en formato '.json'.

🛠️ En este Lab: Se configuró Prefix='incoming/' y Suffix='.json', previniendo activamente bucles infinitos de auto-invocación recursiva.

Log Group Precreado y Retención

Definición: Creación anticipada del contenedor de logs en CloudWatch con política de retención explícita (1 día), acotando los permisos requeridos por el rol de Lambda.

💡 Analogía: Habilitar un cuaderno de registros con vigencia de un día para que el operador solo tenga permiso de escribir, sin facultades para crear cuadernos arbitrarios.

🛠️ En este Lab: Precrear '/aws/lambda/dcl-dev-order-event-s07' permitió retirar 'logs:CreateLogGroup' del rol, dejando únicamente 'CreateLogStream' y 'PutLogEvents'.

Garantía de Entrega At-Least-Once

Definición: Garantía de los sistemas de mensajería distribuida donde AWS asegura que todo evento llegará al menos una vez al consumidor, pudiendo presentar duplicados esporádicos.

💡 Analogía: Un mensajero que ante la duda de si recibiste el mensaje, te entrega una segunda copia de seguridad.

🛠️ En este Lab: La presencia eventual de dos ejecuciones en CloudWatch para un mismo objeto es inherente a la arquitectura distribuida de Amazon S3 y no un error de diseño.

Regla Cardinal · Lab 05

Reachability ≠ Authorization

  • Reachability (Red): Responde "¿Puedo tocar la puerta del servicio?". Si falla, produce Timeout / Could not connect.
  • Identity (Rol IAM): Responde "¿Quién soy?". Entrega credenciales temporales sin almacenar llaves fijas en la instancia.
  • Authorization (Política IAM): Responde "¿Puedo ejecutar esta Action en este Resource?". Si no coincide, devuelve AccessDenied.
  • SSE-S3 vs IAM: Cifrar datos en reposo protege el soporte físico, no sustituye las decisiones de acceso de IAM.
  • CloudTrail Event History: Solo audita Management Events (ej. AttachRolePolicy). No incluye GetObject ni PutObject por ser Data Events.
Regla Cardinal · Lab 06

Template Válido ≠ Infraestructura Operable

  • validate-template únicamente valida la gramática y tipos de datos del YAML; no reserva capacidad ni comprueba permisos.
  • CREATE_COMPLETE valida que los recursos físicos existen; no demuestra que la carga funcione ni que la alarma evalúe adecuadamente.
  • Basic Monitoring: Publica puntos de métrica de EC2 en períodos de 5 minutos (300 s).
  • Alarma 2 de 2: Exige 2 ventanas de 5 min (10 min acumulados). Por ello el script de prueba dura 15 min (900 s).
  • Update sin Reemplazo: Cambiar un Tag (v1 a v2) actualiza la instancia sin modificar su InstanceId físico.
Regla Cardinal · Lab 07

Dos Mecanismos de Permisos Complementarios

  • 1. Resource-based Policy: Autoriza al servicio productor (S3) a invocar la función Lambda.
  • 2. Execution Role: Autoriza a la función Lambda a escribir registros en CloudWatch Logs (CreateLogStream y PutLogEvents).
  • ¿Por qué no hay permisos de S3 en el rol? Porque la función no descarga el archivo; consume el payload inyectado en el evento.
  • Precreación del Log Group: Asegura retención finita de 1 día y evita otorgar el privilegio amplio logs:CreateLogGroup.
